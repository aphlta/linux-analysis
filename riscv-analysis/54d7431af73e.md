## 修改概述

这个patch为RISC-V架构添加了批量TLB刷新支持(BATCHED_UNMAP_TLB_FLUSH)，允许在页面取消映射时延迟TLB刷新操作，从而减少IPI(Inter-Processor Interrupt)数量和sfence.vma指令的执行次数。

## 详细代码分析

### 1. 新增头文件 arch/riscv/include/asm/tlbbatch.h

```c
struct arch_tlbflush_unmap_batch {
    struct cpumask cpumask;
};
```

这个结构体定义了批量TLB刷新的核心数据结构，使用cpumask来跟踪需要进行TLB刷新的CPU集合。

### 2. tlbflush.h 函数声明

新增了四个关键函数的声明：
- `arch_tlbbatch_should_defer()` - 判断是否应该延迟TLB刷新
- `arch_tlbbatch_add_pending()` - 添加待处理的TLB刷新请求
- `arch_flush_tlb_batched_pending()` - 刷新待处理的批量TLB
- `arch_tlbbatch_flush()` - 执行批量TLB刷新

### 3. 核心实现 (tlbflush.c)

#### 3.1 __flush_tlb_range 函数重构

原来的函数签名：
```c
__flush_tlb_range(struct mm_struct *mm, unsigned long start, 
                  unsigned long size, unsigned long stride)
```

新的函数签名：
```c
__flush_tlb_range(const struct cpumask *cmask, unsigned long asid,
                  unsigned long start, unsigned long size, 
                  unsigned long stride)
```

**关键变化**：
- 直接接受cpumask参数，而不是从mm_struct中提取
- 直接接受asid参数，提高了函数的通用性
- 移除了对mm_struct的直接依赖

#### 3.2 调用点更新

所有调用__flush_tlb_range的地方都进行了相应更新：

```c
// 原来
__flush_tlb_range(vma->vm_mm, addr, PAGE_SIZE, PAGE_SIZE);

// 现在
__flush_tlb_range(mm_cpumask(vma->vm_mm), get_mm_asid(vma->vm_mm),
                  addr, PAGE_SIZE, PAGE_SIZE);
```

#### 3.3 批量TLB刷新实现

**arch_tlbbatch_should_defer()**:
```c
bool arch_tlbbatch_should_defer(struct mm_struct *mm)
{
    return true;
}
```
始终返回true，表示RISC-V架构总是支持延迟TLB刷新。

**arch_tlbbatch_add_pending()**:
```c
void arch_tlbbatch_add_pending(struct arch_tlbflush_unmap_batch *batch,
                              struct mm_struct *mm,
                              unsigned long start, unsigned long end)
{
    cpumask_or(&batch->cpumask, &batch->cpumask, mm_cpumask(mm));
    mmu_notifier_arch_invalidate_secondary_tlbs(mm, start, end);
}
```
将需要刷新TLB的CPU添加到批量处理的cpumask中，并通知MMU notifier。

**arch_flush_tlb_batched_pending()**:
```c
void arch_flush_tlb_batched_pending(struct mm_struct *mm)
{
    flush_tlb_mm(mm);
}
```
刷新特定mm_struct的所有待处理TLB。

**arch_tlbbatch_flush()**:
```c
void arch_tlbbatch_flush(struct arch_tlbflush_unmap_batch *batch)
{
    __flush_tlb_range(&batch->cpumask, FLUSH_TLB_NO_ASID,
                      0, FLUSH_TLB_MAX_SIZE, PAGE_SIZE);
    cpumask_clear(&batch->cpumask);
}
```
执行批量TLB刷新，刷新所有累积的CPU上的TLB，然后清空cpumask。

## 技术原理

### 1. 批量TLB刷新机制

传统的TLB刷新是同步的：每次页面取消映射时立即发送IPI到相关CPU执行TLB刷新。这在高频率的页面操作场景下会产生大量的IPI开销。

批量TLB刷新机制的工作原理：
1. **延迟刷新**: 页面取消映射时不立即刷新TLB，而是记录需要刷新的CPU
2. **批量累积**: 将多个取消映射操作的CPU需求累积到一个cpumask中
3. **批量执行**: 在适当的时机一次性刷新所有累积的CPU上的TLB

### 2. RISC-V特定优化

**SBI远程fence优化**:
RISC-V使用SBI (Supervisor Binary Interface) 进行跨CPU的TLB刷新。批量处理可以：
- 减少SBI调用次数
- 降低sfence.vma指令执行频率
- 减少CPU间中断开销

**ASID (Address Space Identifier) 处理**:
- 使用`get_mm_asid()`获取地址空间标识符
- 支持`FLUSH_TLB_NO_ASID`用于内核空间TLB刷新
- 提高TLB刷新的精确性

## 配置要求

在arch/riscv/Kconfig中添加了：
```
select ARCH_WANT_BATCHED_UNMAP_TLB_FLUSH if MMU
```

这表明：
1. 只有在启用MMU的情况下才支持批量TLB刷新
2. 自动选择该特性，无需用户手动配置

## 兼容性和安全性

### 1. 向后兼容性
- 保持了所有现有TLB刷新接口的兼容性
- 不影响现有的单次TLB刷新操作
- 在不支持批量处理的场景下回退到传统方式

### 2. 内存一致性
- 通过`mmu_notifier_arch_invalidate_secondary_tlbs()`确保二级TLB的一致性
- 保证在批量刷新期间的内存访问安全性

### 3. 多核同步
- 使用cpumask精确跟踪需要刷新的CPU
- 确保所有相关CPU的TLB都得到正确刷新

## 总结

这个patch为RISC-V架构实现了高效的批量TLB刷新机制，通过延迟和批量处理TLB刷新操作，显著减少了IPI开销和SBI调用频率。在多线程、高内存操作频率的场景下，性能提升非常显著，特别是在虚拟化环境中效果更加明显。

该实现遵循了Linux内核的通用批量TLB刷新框架，保持了良好的架构一致性和代码可维护性。
